# 反馈闭环开发契约

状态：M1-A 离线接口探针已完成；M1-B 接入小规模开发用 `run` 路径。
这不是正式 Gate，也没有 M1-C 真实模型机制验证或攻击效果结论。

## 要解决的问题

像测试人员根据上一次结果写下一条测试，攻击者需要拿到可辨别的反馈，并把判断落实为实际消息。
只把策略编号交给另一个生成器，会丢失具体测试计划；只检查模型写了证据引用，也不能确认它利用了证据。

`FeedbackAttackDriver.decide()` 接收目标简介、观察、工作状态、当前会话与剩余预算，返回下一步动作
和更新后的状态。开始或继续会话的动作携带可直接发送的消息；结束动作携带原因。调用方负责执行，
再把新观察与状态交回下一次决策。它没有隐藏的跨请求会话。

## 信息契约

`project_attacker_observations()` 必须显式传入 `AttackerVisibility`。Adapter 的插桩能力只限制
可采集的范围，不能自动授予攻击者权限。以下各项仍受 Adapter 可观测性限制：

| 可见性授权 | 攻击者收到什么 |
| --- | --- |
| `response-only` | 已发送消息和目标回复 |
| `tool-calls` | 再加工具名、参数和坏格式计数；执行结果为 `unknown` |
| `tool-status` | 再加 `performed / awaiting_confirmation / rejected / unknown` |
| `support-agent-diagnostics-v1` | 再加自带靶场固定错误类别/说明、模拟副作用种类 |

诊断区分参数错误、权限不足、需要确认、未知工具、资源不存在、金额超限；无法识别的错误给出
`unclassified`。分类仅适用于自带靶场的已知错误格式，不透传原始错误字符串中的私有值。
`performed` 表示工具执行，是否产生违规影响由独立裁判判定。

Policy、评测器答案、reward、Finding、内部停止原因、工具结果正文及副作用 payload 不进入投影。
目标已经回复的内容仍是攻击者可见证据。允许从公开反馈推断规则、测试授权范围内的保密边界；
禁止越过接口读取评测器真值。不能把这两件事混成“禁止寻找受保护信息”。

投影和请求摘要绑定可见性、版本、内容与 Run。当前研究按 Run/seed 隔离状态；这不是对未来产品
跨 Run 学习的永久否决。版本为 `attacker-observation-v2`、`feedback-attacker-prompt-v2`、
`feedback-attacker-choice-v2`；它们属于独立开发接口，不替换旧实验版本。

## 状态与预算契约

工作假设是模型自报判断。引用必须存在于观察账本中，但合法引用不能证明因果推理正确。探索性动作
可以没有引用；将假设状态改为 strengthened、weakened 或 discarded 时需引用观察。六条假设、
每条 300 字符等长度限制是尚未验证的原型参数，正式对照前须登记。

首次调用前检查步骤和 Token；调用后按实际用量决定能否返回动作或进行一次格式修复。预算耗尽抛出
`FeedbackBudgetExhaustedError`，异常保留已发生的成本；未知用量停止处理。预算为零不会调用 Provider，
格式修复耗尽额度也不能再返回可发送动作。

这些是调用准入检查和事后记账。`max_tokens` 限制输出，不能提前约束当前接口无法精确估计的输入
Token，一次在途调用仍可能超额。M1-B 开发运行器累计攻击者（含格式修复）和 Target 的已报告用量，
在每次 Provider 调用前检查 Token、成本与墙钟余额，包括 repair 和 Target 内部工具循环的后续调用。
例如总额度 8 Token，攻击者已用 3、Target 首次调用再用 5，就保留该次工具行为并停止后续调用。
Target 复位和事件落盘后也重新检查墙钟；后续调用失败时保留此前已知用量，未知部分明确标记为未知。
严格的调用前 Token 预留和完整崩溃恢复尚未实现，不能宣称已具备精确的预付费硬封顶。

`decide_with_budget` / `send_with_budget` 接收同一 Run 账本的检查回调，内部传入本次操作累计用量；
只有外层执行器最终记账一次，避免重复计费。多次调用 Provider 的新 Adapter/Driver 必须覆盖该接口，
在各次调用前检查；默认实现只把一个不透明调用视为边界。历史 `decide` / `send` 路径保持原有语义。

## M1-B 小规模开发执行路径

使用 `redcell run --attack-driver feedback` 显式选择反馈驱动器。该路径把驱动器返回的消息送给自带
靶场，并把观察交回下一次决策；旧的 `--search` 路径和历史 Run 不会隐式切换。反馈驱动器、观察权限、
prompt/schema、可见策略名称/描述的有序摘要、工具协议、总决策步数和单场轮数上限均属于新的实验条件。
v5 的策略文本摘要与实际输入在执行前核对；v3/v4 继续使用原有摘要。`--max-tokens` 必须显式设置；
`--budget`、`--max-decision-steps` 和 `--max-turns-per-attempt` 也必须有正数上限，当前默认分别为
20、10 和 3。开发运行建议显式写出四项限制，例如离线验证流水线：

```bash
redcell run --attack-driver feedback --budget 2 --max-tokens 5000 \
  --max-decision-steps 6 --max-turns-per-attempt 2 --seed 0
```

`--feedback-visibility` 默认 `response-only`；需要更详细的工具反馈时，显式选择上表列出的权限，
实际可见内容仍受 Adapter 的采集能力限制。

每次决策和 Target 调用前记录请求，选择与已完成轮次继续追加事件；完成的 Attempt、Finding、Run
状态和事件原子落盘。后端拦下的违规调用仍可成为下一步反馈，不自动结束当前会话；明确的结束出口包括
驱动器结束、确定性实际影响、Token/Attempt/步数/轮数上限和运行故障。未知用量或无法判定的执行失败
按失败记录，不能当作正常完成。当前开发路径要求全新 Run，**不支持 `resume`**；中断后应审计
已有事件，不得把尚未提交的请求当作安全可重试调用。

离线模式只验证消息、观察、预算和落盘流水线，脚本化模型的表现不是安全评估。`--online` 会调用真实
Provider、消耗额度；它也不能替代 M1-C 的目标正常任务 utility 和真实模型机制探针，更不能直接形成
Paper B 或 Gate 的效果结论。M1-B 不负责完整恢复系统与大规模调度。

## 为什么先用这个候选

统一决策把状态更新和消息生成放在同一上下文中，减少一次角色间交接。另一种合理方案是保留
Controller/Generator，让两者共享具体计划、反馈与状态；它更容易复用现有架构，但需要维护交接。
当前选择是为了验证信息能否到达下一步执行，没有证据证明统一角色更有效或更省 Token。

M1-B 只接通小规模开发执行路径。必要的逐步记录和调用边界检查先于真实模型机制探针；完整恢复系统
与大规模调度留待可行性证据后再定范围。

## 验证与指标边界

`tests/test_feedback_attacker.py` 的开发探针保持目标回复文本相同，仅改变结构化反馈。假 Provider
读取实际请求，针对参数错误、权限不足、等待确认、已执行、未知执行状态产生不同后续消息；消息
实际送达测试 Target 后才检查是否对应当前状态。第二次请求计入攻击者和目标的模拟 Token 用量。

负对照忽略反馈但照常给出合法证据引用，五种状态只在预设消息偶然匹配的一种情况下通过。
这证明探针能检测“反馈没有改变动作”，以及接口具备传递该信息的能力；不证明真实 LLM 会形成
正确假设，更不证明攻击成功率提升。这里的 M1-A 探针记录只保存在内存中，不是崩溃恢复证据；
上面的 M1-B 开发路径另行落盘运行事件。

旧 `finding_signature` 包含参数名/类型、影响状态和受保护值摘要，是结构证据变体身份；
`attack_path_signature` 还包含 Strategy ID。两者都不能直接称为根本漏洞数。未来若报告不同违规
边界覆盖，需在评测侧预注册规则/边界 ID 及证据映射，并分别报告实际影响、复现率、重复结果和成本。
此次不修改旧身份算法或冻结实验产物。

设计问答：

- **引用了历史，为什么还不算利用历史？** 忽略反馈的负对照也能抄出合法引用。必须检查改变反馈后，
  实际动作及目标结果是否发生相应变化；真实模型还需独立行为实验。
- **小探针失败是否说明方向不行？** 先区分机制未建立和机制存在但成本收益不足；每次结论只覆盖
  当前模型、可见信息和预算。目标正常任务能力、真实模型机制探针、匹配对照及退出条件仍待单独验证。
